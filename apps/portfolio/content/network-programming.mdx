## HTTP Service Framework

Basic components: 

```mdx
- Request Line
- Request Head
- *[EMPTY LINE]*
- Request Body
```

GET Method Message Example (Dynamic Router):

```mdx
GET /user/729?tag=student HTTP/1.1    // path params (for router) + query params (for HttpServer)
Host: 127.0.0.1:9090
User-Agent: Mozilla/5.0 Chrome
Accept: application/json
Cookie: token=abcd1234
    /* EMPTY LINE */
```

Note that the `?tag=student` in the request line corresponds to **query parameters**: `{"tag" : "student"}`.

POST Method Message Example (Static Router):

```mdx
POST /login HTTP/1.1
Host: 127.0.0.1:9090
Content-Type: application/json
Content-Length: 55
Accept: */*
    /* EMPTY LINE */
{"username":"root","password":"12345678"}    // body params (for HttpServer)
```

### Routing Module

> Route Key = Method + URI

- [x] Static Matching (use hash tables to store):

`handlers_`

| Key | Value |
| --- | --- |
| ("GET","/login") | HandlerPtr A |
| ("POST","/login") | HandlerPtr B |
| ("GET","/user/list") | HandlerPtr C |

`callbacks_`

| Key | Value |
| --- | --- |
| ("GET","/login") | loginPageCallback |
| ("POST","/login") | loginSubmitCallback |
| ("GET","/user/list") | getUserListCallback |

- [x] Dynamic Matching (use vectors to store)

`regexHandlers_`

| Index | Method | Reg. Expr. |
| --- | --- | --- |
| 0 | GET | ^/user/(\d+)$ |
| 1 | GET | ^/article/(\d+)$ |

`regexCallbacks_`

| Index | Callback Func. |
| --- | --- |
| 0 | getUserDetailCallback |
| 1 | getArticleCallback |

- The Procedure of Register:

`addRegexHandler("GET", "user/:uid", [HanlderPtr])` -> `convertToRegex` converts `:uid` to `^/user/([^/]+)$` ->  ("GET", ^/user/([^/]+)$, [HanlderPtr]) is stored in `std::vector<RouteHandlerObj> regexHandlers_`

- The Procedure of `route()`:

`RouteKey{GET, "/user/666"}` -> execute `.find()` in `handlers_` & `callbacks_` -> FAILED -> tranverse the `regexHandlers_` (check method + regx) -> `if (matched)` (check method + `regex_match()`) -> `extractPathParameters(&matchResult, &request)` -> execute `request.setPathParameters("param1", "666")`

Lastly, the router have `req.pathParams["param1"] = "666"` and can call the handler method (where it can access the path parameters) in the object that [HandlerPtr] points to.

> Note: if `user/666/777`, then we also have `req.pathParams["param2"] = "777"`.

### Session Management Module

> How does the HTTP server remember the clients?

> What user status information does the server need to retain?

> Can we verify a user's access permissions based on their information we have on record?

**Basic Classes:**

- [x] `Session` (the atomic component)

Containing:
1. `sessionId_`
2. `data_` : a session-specific KV container that stores user information and temporary page data
3. `maxAge_` & `expiryTime_` : checked by `isExpired()` that is accessible to `SessionManager` & `SessionStorage`
4. `sessionManager_` : to update the stored sessions by indirectly accessing SessionStorage

- [x] `SessionManager` (create, search, destroy Sessions)

Responsible for managing:
1. `sessionId`
2. `Session` & `SessionStorage` objects

Note:
1. The only class have direct access to `SessionStorage`.
2. Can access cookies from `HttpRequest` to get `sessionId`

- [x] `SessionStorage` (abstract) & `MemorySessionStorage` (memory implementation)

It maintains a `std::unordered_map<std::string, std::shared_ptr<Session>> sessions_`.

Is able to:
1. `save(session)`
2. `load(sessionId)` (search corresponding sessions)
3. `remove(sessionId)`


```text
Handlers → ChatServer → HttpServer → SessionManager → SessionStorage
                                          ↑
                Session ─── updateSession ┘
```

### Middleware Module

> We need to preprocess the HttpRequest (parsing, validation and verification) and choose which of them can be sent to Router.

> We need to format the HttpResponse (code, msg, data).

> Need to manage logging.

> Need error handling.

- Base class: `Middleware`; Child class: `CorsMiddleware`

- `CorsMiddleware` overwrite `before()` & `after()` and is only referenced by `ChatServer`; 

`CorsMiddleware` first checks if Method == "OPTIONS" and handle the preflight request. If yes, it then verifies the **Origin, Method and Headers** of the preflight request against `allowedMethods` and `allowedHeaders`. If all checks pass, the `CorsMiddleware` writes all CORS-related headers to the response, returns early to **skip the Router**.

For the preflight request: 
```cpp
addCorsHeaders(response, request.getHeader("Origin")); // add it back the way it was
```

For the normal requests: 
```cpp
addCorsHeaders(response, "*"); // default configuration
```

- `CorsConfig` records `allowedOrigins`, `allowedMethods` and `allowedHeaders`

- `MiddlewareChain` uses `vector<shared_ptr<Middleware>>` to store `Middleware`s and call their `before()` & `after()` in a special order:

```text
A.before → B.before → Handlers → B.after → A.after
```

### Integrated Database Connection Pool Module

Database is a disk, I/O operation is resource-consuming. Therefore, we need cache system (Redis or memory cache, usually in **KV entries**), or MySQL (in **2D tables**).

**Connection pool** allows applications to **reuse** an existing database connection.

The Process of Executing an SQL Statement:

1. Establish a connection via the TCP 3-way handshake
2. MySQL authenticates the connection and **allocates the necessary resources**
3. **Execute the SQL statement**
4. Close the MySQL connection and **reclaim the necessary resources**
5. Close the connection via the TCP 4-way handshake

How a Database Connection Pool Works:

1. Create a connection pool (`vector`, `queue`, etc.)
2. **Manage the usage of the connection** (available? -> max connections? -> create a new connection / wait -> max time? -> exception)
3. Close the coonection pool (close all connections, free all resources)

```text
Handlers / ChatServer
        ↓
    MysqlUtil
        ↓
 DbConnectionPool（Global Singleton Pattern）
        ↓
   DbConnection（single MySQL connection）
        ↓
       MySQL
```

**In `DbConnection`**:

1. Two critical functions: 
```cpp
executeQuery(sql, args...);  // SELECT
    return stmt->executeQuery();
executeUpdate(sql, args...); // INSERT / UPDATE / DELETE
    return stmt->executeUpdate();
```

2. Use mutex lock while accessing MySQL:
```cpp
std::lock_guard<std::mutex> lock(mutex_);
```

3. It also provides `ping()`, `reconnect()`, `cleanup()`, for healthy check, reconnection and cleaning up resources.

**`DbConnectionPool` is a process-level singleton instance**
